## 규칙: 매직 넘버(Magic Number)에 의미 있는 이름 붙이기

### 왜 필요한가 (가독성)

매직 넘버란, **숫자의 의미를 설명하지 않고 코드 안에 직접 박아 넣은 값**을 말합니다.

- 예: `404`(Not Found), `86400`(하루를 초 단위로 표현), `300`(지연 시간) 등을 그대로 사용하는 것

코드에 맥락 없이 숫자만 적혀 있으면:

- “이 값이 **무엇을 의미하는지**”
- “왜 **이 숫자**가 선택되었는지”
- “다른 곳과 **연관된 값인지**(공식/비즈니스 규칙 등)”

를 알기 어렵습니다.  
숫자에 **이름을 붙인 상수**를 사용하면, 코드의 의도와 맥락을 즉시 파악할 수 있습니다.

---

## 코드 예시: 좋아요 버튼

### 안티 패턴 예시

```ts
async function onLikeClick() {
  await postLike(url);
  await delay(300);
  await refetchPostLike();
}
```

### 문제점 (냄새)

- `delay(300)` 의 **300이 무엇을 의미하는지** 코드만 봐서는 알 수 없습니다.
  - 애니메이션이 끝날 때까지 기다리는 시간인가?
  - 서버에서 좋아요 반영이 안정화될 때까지의 지연인가?
  - 테스트 코드에서 임시로 넣었다가 깜빡 잊고 안 지운 값인가?
- 여러 개발자가 함께 작업할 때:
  - 의도를 모른 채 이 값을 변경하거나 삭제하면,
  - 원래 의도와 다르게 동작하게 될 위험이 있습니다.

또한, 이 숫자가 **여러 곳에서 중복**으로 사용된다면:

- 일부만 바꾸고 일부는 안 바꾸는 실수가 생기기 쉽고,
- “이 숫자들이 사실 하나의 개념(예: 애니메이션 지연 시간)”이라는 사실을 파악하기 어렵습니다.

---

### 개선안: 상수에 이름 붙이기

```ts
const ANIMATION_DELAY_MS = 300;

async function onLikeClick() {
  await postLike(url);
  await delay(ANIMATION_DELAY_MS);
  await refetchPostLike();
}
```

- `ANIMATION_DELAY_MS` 라는 이름만 봐도:
  - “애니메이션이 끝날 때까지 기다리기 위한 지연 시간”이라는 의미를 바로 이해할 수 있습니다.
- 이후 이 값을 변경하거나, 다른 곳에서 동일한 개념을 사용할 때도
  - 상수 하나만 수정하면 되고
  - 코드 전반의 의도가 더 명확해집니다.

## 언제 매직 넘버에 이름을 붙일까?

### 이름을 붙이는 것이 좋은 경우

1. **도메인/비즈니스 규칙과 관련된 숫자**
   - 예: 최소 주문 금액, 무료 배송 기준 금액, 최대 수량, 포인트 적립 비율 등
   - → `MIN_ORDER_AMOUNT`, `FREE_SHIPPING_THRESHOLD`, `MAX_QUANTITY`, `POINT_RATE` 등으로 상수화

2. **시간/횟수/크기 등 단위가 있는 숫자**
   - 예: `300`(ms), `5`(회), `10`(개), `0.1`(비율) 등
   - → `ANIMATION_DELAY_MS`, `MAX_RETRY_COUNT`, `DEFAULT_PAGE_SIZE`, `DISCOUNT_RATE` 등으로 명시

3. **여러 곳에서 반복해서 쓰이는 숫자**
   - 예: 같은 파일/모듈/도메인에서 `300` 이 여러 번 등장하는 경우
   - → 공통 상수로 추출해 “같은 개념”임을 드러내고, 변경 시 하나만 수정할 수 있게 합니다.

4. **코드 리뷰 때 “이 숫자는 뭐지?” 라는 질문이 나올 법한 숫자**
   - 리뷰어 입장에서 질문이 생길 것 같다면, 상수 이름으로 답을 미리 적어두는 것이 좋습니다.

### 이름을 붙이지 않아도 괜찮은 경우

1. **완전히 자명한 리터럴**

```ts
const items = Array(3).fill(null);
for (let i = 0; i < 2; i++) { ... }
```

- 아주 짧은 스코프 안에서 “단순 카운트/인덱스”로 쓰이는 `0`, `1`, `2`, `3` 등은  
  굳이 상수로 추출하지 않아도 맥락 상 명확한 경우가 많습니다.

2. **테스트 코드에서만 쓰이는 임의의 값**

```ts
const result = add(1, 2);
expect(result).toBe(3);
```

- 의미보다는 동작을 검증하기 위한 숫자는, 오히려 직관적인 예시로 남겨두는 편이 더 나을 수 있습니다.

## 이 프로젝트에서의 적용 원칙

1. **시간 관련 숫자는 모두 단위까지 포함해서 상수로**
   - 예: `150`, `300`, `1000` 같은 ms 단위 숫자는
     - `SCROLL_THROTTLE_MS`, `ANIMATION_DURATION_MS`, `TOAST_DURATION_MS` 처럼
     - “무엇에 쓰이는지 + 단위”를 함께 표현합니다.

2. **도메인 규칙 숫자는 `constants` 영역으로 모으기**
   - 최소/최대 수량, 가격 관련 기준값 등은
     - `src/constants` 아래에서 의미 있는 이름으로 관리하고,
     - 비즈니스 규칙이 바뀌었을 때 한 곳에서만 수정되도록 합니다.

3. **같은 숫자가 2곳 이상에 등장하면 반드시 상수 추출 검토**
   - 검색(`grep`)에서 같은 숫자가 여러 번 나올 경우,
     - “정말 우연히 같은 값인지?”
     - “실제로는 같은 개념인데 흩어져 있는지?”
     를 점검하고, 후자라면 공통 상수로 추출합니다.

4. **리뷰 시 체크 포인트**
   - 코드 리뷰할 때 다음을 스스로/서로에게 물어봅니다.
     - “이 숫자는 **무엇을 의미하는지** 이름만 보고 알 수 있는가?”
     - “나(또는 다른 팀원)가 1개월 뒤에 다시 봐도 이해할 수 있을까?”
   - “아니다” 싶으면 → 의미 있는 이름의 상수로 교체합니다.

이 원칙을 지키면, 숫자 자체가 아니라 **숫자가 표현하는 개념**이 코드에 드러나기 때문에,  
코드의 의도와 비즈니스 규칙을 더 쉽게 이해하고 안전하게 수정할 수 있습니다.
