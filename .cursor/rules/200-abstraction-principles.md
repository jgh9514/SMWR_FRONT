# 추상화 원칙 (Abstraction Principles)

## 핵심 원칙

### 1. 추상화 vs 추출
- **추상화**: 책임 단위로 구조를 재설계하는 것
  - 핵심 개념을 먼저 정의하고 필요한 정보만 외부에 노출
  - 나머지 구현은 내부에 감춤
  - 구조와 의미를 재정의
  
- **추출**: 모양만 분리하는 것 (피해야 함)
  - 책임 정의 없이 "길어서", "보기 불편해서" 나누는 경우
  - 구조적 의미 없이 파일과 함수만 증가
  - "이걸 왜 나눴지?"라는 찝찝함을 남김

### 2. 역할을 드러내고, 구현은 숨겨라
- **드러내야 하는 것 (What)**: 기능의 핵심 역할
- **감춰야 하는 것 (How)**: 내부 구현

```typescript
// ✅ 좋은 예: 역할이 명확함
function sum(arr: number[]): number {
  // 내부 구현은 숨김
}

// ❌ 나쁜 예: 구현이 드러남
function sumWithForLoop(arr: number[]): number {
  // 함수명에 구현 방식이 드러남
}
```

### 3. 구조를 먼저 설계하고 구현은 나중에
작업 순서:
1. 요구사항 분석
2. 현재 구조 파악
3. 이상적인 UI·상태·동작 모델 설계
4. 구현 시작

**중요**: 구현된 화면부터 보면 바로 코딩하고 싶어진다. 구조를 먼저 생각해야 한다.

### 4. HTML 인터페이스를 활용한 설계
- HTML은 이미 전 세계적으로 합의된 인터페이스
- 태그마다 역할과 속성이 명확하게 정의되어 있음
- 새로운 규칙을 만드는 것보다 이미 합의된 인터페이스를 활용하라

```typescript
// ✅ 좋은 예: HTML 속성을 그대로 활용
interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: 'primary' | 'secondary';
}

// ❌ 나쁜 예: 새로운 규칙을 만들어 혼란 야기
interface ButtonProps {
  onClickAction?: () => void; // onClick 대신 새로운 이름 사용
}
```

### 5. 인터페이스는 "계약"이다
- 이름만으로 역할이 떠오르지 않는다면 협업 비용이 증가
- 인터페이스는 이름만으로도 계약이 성립해야 함

```typescript
// ✅ 좋은 예: 이름만으로 역할이 명확
function ErrorBoundary({ children }: { children: React.ReactNode }) {
  // Error Boundary라는 이름으로 역할이 명확
}

// ❌ 나쁜 예: 이름이 모호함
function Boundary({ children }: { children: React.ReactNode }) {
  // 무엇을 하는 Boundary인지 불명확
}
```

### 6. 파일 분리는 "의미가 생겼을 때"
- 단순히 코드가 길어서 나누는 건 추출일 뿐
- 책임이 명확해졌을 때 비로소 분리해야 추상화가 됨

### 7. Monster Hook 피하기
- 여러 책임을 한 훅에 몰아넣으면 예측 가능성·확장성·테스트 용이성이 모두 떨어짐
- 훅은 작고 명확하게 유지

```typescript
// ❌ 나쁜 예: 여러 책임을 가진 Monster Hook
function useUserData() {
  // 사용자 정보 조회
  // 사용자 설정 조회
  // 사용자 알림 조회
  // 사용자 길드 조회
  // ... 너무 많은 책임
}

// ✅ 좋은 예: 책임이 명확한 작은 훅들
function useUserInfo() { /* 사용자 정보만 */ }
function useUserSettings() { /* 설정만 */ }
function useUserNotifications() { /* 알림만 */ }
```

### 8. 전역 상태는 최소화
- 전역 상태는 강력하지만 파급 범위가 넓음
- 조금만 남용해도 전체 구조의 예측 가능성을 해침

### 9. UI 구조와 코드 구조는 1:1로 대응
- UI의 위계와 코드의 위계를 일치시켜야 함
- 구조가 일치하면 예측 가능성이 높아짐

### 10. 재사용성은 목표가 아니라 결과물
- 책임 단위로 추상화하면 자연스럽게 재사용 가능한 코드가 됨
- 재사용을 목표로 하면 오히려 과도한 추상화가 발생할 수 있음

## 실무 적용 체크리스트

코드를 작성하기 전에 다음 질문을 던져보자:

1. 이 기능의 핵심 책임은 무엇인가?
2. 외부에 노출해야 하는 정보는 무엇인가?
3. 감춰야 할 구현(How)은 무엇인가?
4. 지금 하고 있는 것은 추출인가, 추상화인가?
5. 이름만으로 역할이 명확한가?
6. UI 구조와 코드 구조가 일치하는가?

## 핵심 인사이트

1. 기능 요구사항을 기반으로 이상적인 구조를 먼저 설계한다.
2. UI 구조와 코드 구조는 1:1로 대응되도록 만든다.
3. 재사용성은 목표가 아니라 결과물이다. 책임 단위로 추상화하면 자연스럽게 따라온다.

**결론**: "역할과 구조가 명확한 코드가 예측 가능성을 만든다."
