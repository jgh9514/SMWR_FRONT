## 규칙: 불필요한 결합을 만들 바엔, 중복 코드를 허용하기

### 왜 필요한가 (결합도)

여러 페이지/컴포넌트에 걸친 비슷한 코드를 보면,

- “이걸 공통 Hook/컴포넌트로 빼야 하지 않을까?”라는 생각이 자연스럽게 듭니다.

공통화의 장점:

- 함께 수정되어야 할 코드를 한 곳에서 관리할 수 있고
- 동일한 로직/뷰를 일관성 있게 유지할 수 있습니다.

하지만, **성급한 공통화는 불필요한 결합도를 만들어**:

- 공통 코드를 변경할 때 영향을 받는 범위를 과도하게 넓히고
- 페이지별 특수 요구사항이 생길수록 공통 코드가 점점 복잡해지며
- 결국 “아무도 건드리기 싫은 코드 덩어리”가 되기 쉽습니다.

> “진짜로 같은 동작을 지금도, 앞으로도 할 것인가?”를 확인하기 전까지는  
> **일부 중복을 허용**하는 편이 더 안전할 수 있습니다.

## 코드 예시: 점검 바텀시트 공통 Hook

### 공통화된 Hook 예시

```ts
export const useOpenMaintenanceBottomSheet = () => {
  const maintenanceBottomSheet = useMaintenanceBottomSheet();
  const logger = useLogger();

  return async (maintainingInfo: TelecomMaintenanceInfo) => {
    logger.log("점검 바텀시트 열림");
    const result = await maintenanceBottomSheet.open(maintainingInfo);
    if (result) {
      logger.log("점검 바텀시트 알림받기 클릭");
    }
    closeView();
  };
};
```

- 점검 정보를 받아:
  - 점검 바텀시트를 열고
  - 사용자가 “알림 받기”를 누르면 로깅하고
  - 이후 현재 화면을 닫는 공통 Hook입니다.
- 여러 페이지에서 같은 패턴으로 사용되기 때문에 공통화된 상태입니다.

### 문제점 (냄새)

지금은 같아 보이는 동작이라도, 앞으로 이런 요구가 생길 수 있습니다:

- 페이지마다 **로깅하는 값이 달라진다면?**
- 어떤 페이지에서는:
  - 점검 바텀시트를 닫더라도 **화면은 닫지 않아야** 한다면?
- 바텀시트에 보여줄 텍스트/이미지가:
  - 페이지마다 다르게 구성되어야 한다면?

이런 요구가 하나둘 생길수록:

- 이 Hook은
  - 로깅 키, 화면 닫힘 여부, 바텀시트 컨텐츠 등을 인자로 받는
  - 매우 복잡한 “만능 Hook”으로 변해갑니다.
- 이 Hook을 수정할 때마다:
  - 이 Hook을 사용하는 **모든 페이지를 일일이 확인/테스트**해야 합니다.

즉, **공통화가 결합도를 과도하게 높이고**, 변경이 어려운 코드로 이어질 위험이 있습니다.

## 언제 중복을 허용하는 것이 더 나은가?

다음 질문에 “예”라고 답할 수 없다면, **공통화 대신 중복을 유지**하는 편이 낫습니다.

1. **로깅/동작/모양이 지금도, 앞으로도 정말 같을까?**
   - 로깅 키, 버튼 텍스트, 동작(화면 닫기 여부)이
     - 모든 페이지에서 동일하고
     - 비즈니스 상으로도 함께 바뀔 가능성이 높다면 공통화 후보입니다.
   - 반대로, 페이지별로 “조금씩 다르게 하고 싶다”는 요구가 이미 있거나 생길 것 같다면,
     - 공통화하지 않고 페이지별로 코드를 유지하는 편이 더 안전합니다.

2. **공통 코드를 수정할 때, 항상 함께 테스트할 수 있는 범위인가?**
   - 공통 Hook/컴포넌트를 수정하면:
     - 그 Hook을 사용하는 모든 페이지/컴포넌트가 영향을 받습니다.
   - 현실적으로 모든 사용처를 항상 충분히 테스트하기 어렵다면,
     - 공통화가 오히려 리스크가 됩니다.

## 가이드라인: 공통화 vs 중복 허용

### 공통화를 선택할 때

- 비즈니스 상으로 “같은 개념”이고, **동일한 동작을 지금도·미래에도 강하게 요구**하는 경우
  - 예: 완전히 동일한 디자인/동작을 갖는 공통 버튼, 전역 알림 바텀시트, 통일된 포맷터 등
- 바뀔 때 항상 **함께 바뀌는 것을 원한다**고 팀이 합의할 수 있는 경우

### 중복을 허용할 때

- 페이지마다 동작/로깅/UI가 **조금씩 달라질 여지**가 있는 패턴
  - 예: “점검 바텀시트”가 페이지마다 문구/이미지/로깅/화면 닫기 여부가 달라질 수 있는 경우
- 공통화하면:
  - Hook/컴포넌트가 인자/옵션으로 가득 차서 복잡해질 것 같은 경우
  - 수정 시마다 영향을 받는 사용처가 너무 많아지는 경우

## 이 프로젝트에서의 적용 원칙

1. **“한 번 더 보이는 비슷한 코드”를 공통화하기 전에 질문하기**
   - “지금 이 두 곳의 코드가 비슷해 보이지만, **진짜로 같은 개념/동작인가?**”
   - “앞으로도 함께 바뀌어야 하는가, 아니면 페이지별로 다르게 진화할 여지가 있는가?”

2. **공통 Hook/컴포넌트는 도메인/UX적으로 강하게 묶일 때만 만든다**
   - 단순히 “모양이 비슷하다”는 이유만으로 공통화하지 않습니다.
   - 그 패턴이 **도메인 상의 개념**인지, **UX 가이드로 고정된 것인지**를 먼저 확인합니다.

3. **이미 공통화된 코드가 점점 복잡해진다면 분리 검토**
   - 인자가 계속 늘어나고, 조건 분기가 많아진다면:
     - 이미 과도한 결합이 생겼다는 신호입니다.
   - 이 경우:
     - 사용처별로 코드를 되돌려 분리하거나,
     - 더 작은 단위의 공통 요소(예: 순수 UI 컴포넌트만)로 다시 쪼개는 것을 고려합니다.

4. **“중복이 있다”는 이유만으로 리팩터링 목표를 삼지 않기**
   - 리팩터링의 1차 목표는 **이해/수정하기 쉬운 코드**입니다.
   - 중복 제거는 그 수단일 뿐이며,
     - 불필요한 결합도를 만드는 공통화는 피하는 것이 좋습니다.

이 원칙을 따르면, 중복을 없애는 것보다 **유지보수성과 안정성**을 우선하면서,  
필요할 때만 신중하게 공통화를 도입하는 방향으로 코드 구조를 설계할 수 있습니다.
