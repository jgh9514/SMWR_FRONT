## 규칙: 이름/시그니처에 드러나지 않는 숨은 로직을 감추지 않기

### 왜 필요한가 (예측 가능성)

함수나 컴포넌트의 **이름, 파라미터, 반환 타입만 봐서는 보이지 않는 숨은 로직**이 있으면:

- 동료들이 함수의 동작을 예측하기 어렵고
- 의도치 않은 부작용(로깅, 네트워크 호출, 전역 상태 변경 등)이 발생할 수 있으며
- 해당 숨은 로직의 장애가 원래 기능까지 망가뜨리는 위험을 키웁니다.

> 함수/컴포넌트는 **이름과 시그니처로 예측할 수 있는 일만** 하도록 유지하는 것을 목표로 합니다.

---

## 코드 예시: 잔액 조회 + 숨은 로깅

### 안티 패턴 예시

```ts
async function fetchBalance(): Promise<number> {
  const balance = await http.get<number>("...");

  logging.log("balance_fetched");

  return balance;
}
```

### 문제점 (냄새)

- `fetchBalance` 의 이름/시그니처만 보면:
  - “잔액을 가져와서 숫자를 반환하는 함수”라고만 예상됩니다.
- 실제로는:
  - `logging.log("balance_fetched")` 라는 **로깅 부작용**이 숨어 있습니다.
  - 로깅이 필요 없는 곳에서도 이 함수를 쓰면 **원치 않는 로그**가 남습니다.
  - 로깅 코드에 문제가 생기면 **잔액 조회 기능까지 함께 망가질** 수 있습니다.

즉, 이 함수는 “잔액 조회”와 “로깅” 이라는 **두 가지 역할**을 동시에 떠안고 있고,  
그 중 하나(로깅)는 이름/시그니처에서는 전혀 드러나지 않는 **숨은 로직**입니다.

## 개선안: 숨은 로직 분리하기

### 1) 함수는 “잔액 조회”만 책임지도록 단순화

```ts
async function fetchBalance(): Promise<number> {
  const balance = await http.get<number>("...");

  return balance;
}
```

- 이제 `fetchBalance` 는 이름 그대로:
  - “잔액을 가져온다”
  - “숫자를 반환한다”
  라는 역할에만 집중합니다.

### 2) 로깅은 호출하는 쪽에서 명시적으로 수행

```tsx
<Button
  onClick={async () => {
    const balance = await fetchBalance();
    logging.log("balance_fetched");

    await syncBalance(balance);
  }}
>
  계좌 잔액 갱신하기
</Button>
```

- 이제 이 버튼을 읽는 사람은:
  - 클릭 시
    - 잔액을 가져오고
    - `balance_fetched` 로그를 남기고
    - `syncBalance` 를 호출한다
  는 **전체 동작을 한눈에 이해**할 수 있습니다.
- 로깅이 필요 없는 다른 곳에서는:

```ts
const balance = await fetchBalance(); // 로깅 없음
```

처럼 부작용 없이 사용할 수 있습니다.

## 이 프로젝트에서의 적용 원칙

1. **이름/시그니처에서 전혀 예상되지 않는 부수 효과는 숨기지 않는다**
   - 예: `fetchXxx` / `getXxx` 같이 “데이터 읽기”로 보이는 함수가:
     - 로깅, 트래킹, 토스트, 라우팅 변경, 전역 상태 변경, alert 등 **쓰기/부수 효과**를 몰래 수행하지 않도록 합니다.
   - 꼭 함께 수행해야 한다면:
     - `fetchBalanceWithLogging`, `syncAndLogBalance` 처럼 이름에 드러나게 하거나,
     - 호출하는 쪽으로 부수 효과를 옮깁니다.

2. **로깅/트래킹은 가능하면 “사용자 액션” 쪽에 붙이기**
   - 버튼 클릭, 폼 제출, 특정 UI 인터랙션 등
     - 사용자 액션이 일어나는 지점에서
     - 로깅/트래킹을 명시적으로 호출합니다.
   - 데이터 조회/계산 함수에는:
     - 해당 액션과 직접적으로 연결된 부수 효과를 숨겨 넣지 않습니다.

3. **숨은 로직이 필요한 경우, 더 구체적인 이름으로 분리**
   - “진짜로 이 함수가 항상 로깅까지 포함해야 한다”면:
     - `fetchBalanceAndLog` 처럼 동작을 이름에 드러내거나,
     - `withBalanceFetchedLogging(fetchBalance)` 같은 래퍼/HOC 패턴을 명시적으로 사용합니다.

4. **리뷰 시 체크 포인트**
   - “이 함수/컴포넌트 이름과 시그니처만 봤을 때, 실제 동작을 충분히 예측할 수 있는가?”
   - “숨은 로깅/트래킹/라우팅 변경/전역 상태 변경이 숨어 있지는 않은가?”

이 원칙을 지키면, 각 함수/컴포넌트의 역할이 더 명확해지고,  
동작을 예측하기 쉬워져 협업과 디버깅이 훨씬 수월해집니다.
