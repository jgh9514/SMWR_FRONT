## 규칙: 함께 수정되는 파일은 같은 디렉토리에 모으기

### 왜 필요한가 (응집도)

프로젝트가 커질수록:

- Hook, 컴포넌트, 유틸, 상수 등이 **여러 파일/폴더로 분산**되고
- 어떤 코드가 어떤 코드에 의존하는지 파악하기 어려워지며
- 더 이상 사용되지 않는 코드가 여기저기 남기 쉽습니다.

함께 수정되는 파일을 하나의 디렉토리 아래에 모으면:

- **코드 사이 의존 관계를 더 쉽게 파악**할 수 있고
- 참조하면 안 되는 다른 도메인/레이어를 잘못 참조하는 것을 발견하기 쉬우며
- 특정 기능/도메인을 지울 때 **디렉토리 단위로 깔끔하게 삭제**할 수 있습니다.

---

## 안티 패턴 예시: 종류별(global) 디렉토리 구조

```text
└─ src
   ├─ components
   ├─ constants
   ├─ containers
   ├─ contexts
   ├─ remotes
   ├─ hooks
   ├─ utils
   └─ ...
```

### 문제점 (냄새)

- 파일이 “종류별”로만 나뉘어 있어서:
  - 어떤 기능/도메인에 속하는지
  - 어떤 파일들이 함께 동작/수정되는지
  를 디렉토리만 보고는 알 수 없습니다.
- 코드 파일 사이의 의존 관계를:
  - 디렉토리 구조가 아니라
  - **개발자가 직접 머리로 추적**해야 합니다.
- 특정 컴포넌트/Hook/유틸이 더 이상 쓰이지 않아 삭제하려고 할 때:
  - 연관된 코드가 다른 디렉토리에 흩어져 있어
  - 일부만 삭제되고, 사용되지 않는 코드가 남을 가능성이 큽니다.
- 프로젝트가 2배, 10배, 100배 커지면:
  - `components`, `hooks`, `utils` 같은 디렉토리에
  - **수십~수백 개 파일이 쌓여서** 관리/탐색이 어려워집니다.

## 개선 예시: 도메인별 디렉토리 구조 + 내부 타입별 구분

```text
└─ src
   │  // 전체 프로젝트에서 공용으로 사용하는 코드
   ├─ components
   ├─ containers
   ├─ hooks
   ├─ utils
   ├─ ...
   │
   └─ domains
      │  // Domain1에서만 사용되는 코드
      ├─ Domain1
      │     ├─ components
      │     ├─ containers
      │     ├─ hooks
      │     ├─ utils
      │     └─ ...
      │
      │  // Domain2에서만 사용되는 코드
      └─ Domain2
            ├─ components
            ├─ containers
            ├─ hooks
            ├─ utils
            └─ ...
```

### 장점

- **같은 도메인/기능에서 함께 쓰이고 함께 수정되는 파일**을 한 디렉토리에 모을 수 있습니다.
- 예를 들어 Domain1 코드가 Domain2 코드를 잘못 참조하면:

```ts
import { useFoo } from "../../../Domain2/hooks/useFoo";
```

  - 이런 import를 보는 순간, “다른 도메인에 과하게 의존하고 있다”는 것을 쉽게 눈치챌 수 있습니다.
- 특정 기능/도메인을 삭제할 때:
  - 해당 도메인 디렉토리를 통째로 삭제함으로써
  - 관련된 코드가 **깔끔하게 모두 제거**됩니다.

---

## 이 프로젝트에서의 적용 원칙

1. **도메인(기능) 중심으로 상위 디렉토리를 나누기**
   - 예: `catalog/`, `order/`, `user/` 등
   - 각 도메인 내부에서 다시 `components/`, `hooks/`, `utils/` 로 나누어도 됩니다.

2. **전역 공용 코드와 도메인 전용 코드를 분리**
   - `src/components`, `src/hooks`, `src/utils` 등은:
     - 여러 도메인에서 공통으로 사용하는 코드만 위치시킵니다.
   - 특정 도메인에서만 사용되는 컴포넌트/Hook/유틸은:
     - 해당 도메인 디렉토리 아래로 내려보냅니다.

3. **import 경로로 의존 관계를 점검**
   - 상대 경로가 너무 길어지거나(`../../../Domain2/...`)  
     다른 도메인 디렉토리를 가리키면:
     - “이 참조가 정말 필요한지”
     - “공용 계층으로 추출해야 하는지”
     를 점검하는 신호로 삼습니다.

4. **기능 삭제 시 디렉토리 단위로 제거**
   - 특정 기능/도메인이 완전히 필요 없어졌다면:
     - 해당 디렉토리를 통째로 삭제하는 방식으로 정리합니다.
   - 함께 수정/배포되던 파일들이 한 곳에 모여 있으므로,
     - 사용되지 않는 코드가 남을 확률을 줄일 수 있습니다.

이 원칙을 지키면, 디렉토리 구조 자체가 **코드의 의존 관계와 응집도**를 표현하게 되고,  
팀원들이 기능 단위로 코드를 이해하고 수정/삭제하기 훨씬 쉬워집니다.
