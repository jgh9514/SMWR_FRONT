## 규칙: 매직 넘버를 없애고, 변경 지점을 한 곳으로 모으기

### 왜 필요한가 (응집도)

매직 넘버(Magic Number)는 **정확한 뜻을 밝히지 않고 소스 코드 안에 직접 적어 넣은 숫자 값**을 말합니다.

- 예: HTTP 404(찾을 수 없음), 하루를 표현하는 `86400`(초 단위) 등을 그대로 사용하는 것

이 숫자들이 **어떤 맥락에서 쓰였는지** 드러나 있지 않으면:

- 나중에 관련 로직을 수정할 때, 어디를 고쳐야 하는지 찾기 어렵고
- “함께 수정되어야 할 코드” 중 일부만 수정되어 조용히 서비스가 깨질 수 있습니다.

> 매직 넘버를 없애고, 의미 있는 상수/단일 변경 지점(single source of truth)으로 모으면  
> 관련된 코드가 **함께 수정되는 응집도 높은 구조**를 만들 수 있습니다.

---

## 코드 예시: 좋아요 버튼 + 지연 시간

### 안티 패턴 예시

```ts
async function onLikeClick() {
  await postLike(url);
  await delay(300);
  await refetchPostLike();
}
```

### 문제점 (냄새)

- `300` 이라는 숫자가:
  - 애니메이션이 끝날 때까지 기다리는 시간인지,
  - 서버에서 좋아요 반영을 기다리는 시간인지,
  - 테스트용 임시 값인지 알 수 없습니다.
- 특히, 이 값이 **애니메이션 완료를 기다리기 위한 시간**이라면:
  - 애니메이션 길이를 변경했을 때
    - 이 300을 함께 고치지 않으면
    - 애니메이션이 끝나기 전에 다음 로직이 실행되거나,
    - 불필요하게 오래 기다리는 문제가 생깁니다.
- 즉, 애니메이션 코드와 지연 시간 숫자가 **서로 응집**되어 있으면서도,
  - 한쪽만 수정될 수 있는 구조라 **응집도가 낮은 코드**가 됩니다.

## 개선안: 의미 있는 상수로 추출하기

```ts
const ANIMATION_DELAY_MS = 300;

async function onLikeClick() {
  await postLike(url);
  await delay(ANIMATION_DELAY_MS);
  await refetchPostLike();
}
```

- `ANIMATION_DELAY_MS` 라는 이름을 통해:
  - “애니메이션 지연 시간”이라는 맥락을 명확히 드러냅니다.
- 나중에 애니메이션이 바뀌면:
  - 이 상수 하나만 고치면 되므로
  - 관련된 코드가 **함께 수정되는 응집도 높은 구조**가 됩니다.

또한, 이 상수를 실제 애니메이션 설정과 **같은 파일/모듈**에 두면:

- 애니메이션 길이를 변경할 때 지연 시간도 같이 보면서 수정할 수 있어
  - 변경 누락을 줄일 수 있습니다.

---

## 이 프로젝트에서의 적용 원칙

1. **의미 있는 숫자는 모두 상수로 모으기**
   - 애니메이션 시간, 토스트 노출 시간, API 타임아웃, 재시도 횟수, 최소/최대 값 등은:
     - 이름 있는 상수(예: `ANIMATION_DELAY_MS`, `TOAST_DURATION_MS`, `API_TIMEOUT_MS`)로 정의합니다.
   - 가능한 한 관련 로직과 **같은 모듈/도메인**에 상수를 두어, 함께 수정되게 합니다.

2. **관련 코드와 상수를 최대한 가까이에 두기**
   - 특정 UI/애니메이션/도메인에서만 쓰이는 상수는:
     - 해당 UI/도메인 디렉토리(예: `domains/order/constants.ts`)에 두고,
     - 전역 상수 파일 하나에 모든 숫자를 몰아넣지 않습니다.

3. **숫자가 두 곳 이상에서 쓰이면 더 강하게 상수 추출 검토**
   - 같은 숫자가 여러 곳에서 쓰인다면:
     - 우연히 같은 값인지,
     - 실제로 같은 개념(예: 동일한 지연 시간/제한 값)인지 확인하고,
     - 후자라면 **하나의 상수로 모아 응집도를 높입니다.**

4. **매직 넘버를 발견했을 때의 리팩터링 순서**
   1. 이 숫자가 **무엇을 의미하는지** 먼저 명확히 정의한다.
   2. 의미를 반영한 상수 이름을 정한다. (예: `MAX_RETRY_COUNT`, `ORDER_MIN_AMOUNT`)
   3. 관련된 코드와 가까운 위치에 상수를 선언한다.
   4. 원래 숫자를 모두 상수로 치환한다.

이 원칙을 지키면, 숫자 변경 시 관련 코드를 **한 번에 안전하게 수정**할 수 있고,  
숫자가 표현하는 비즈니스/UX 맥락도 코드에 잘 드러나 응집도가 높아집니다.
